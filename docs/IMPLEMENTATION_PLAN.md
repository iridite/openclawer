# OC-Deploy 实施计划

更新时间：2026-03-18

本文档基于 [PROJECT_ANALYSIS.md](./PROJECT_ANALYSIS.md) 的结论，将当前项目的主要优化方向收敛为一份可执行实施计划。

目标不是一次性重构全部系统，而是在不破坏当前可用性的前提下，按优先级逐步提升：

- 配置一致性
- 前端可维护性
- 备份/升级可靠性
- 测试深度
- 接口语义清晰度

## 实施原则

### 1. 先稳后快

当前项目已经可用，不能为了“更优雅”而破坏现有安装、升级、代理和管理链路。实施顺序应优先处理结构性风险，再做体验类优化。

### 2. 优先消除重复源

任何默认值、备份边界、状态判断逻辑，如果存在多处重复实现，优先统一来源，而不是继续在多个位置同步维护。

### 3. 保持现有产品边界

本计划不改变以下项目决策：

- OC-Deploy 继续作为部署编排器与运维面板
- OpenClaw 原生 dashboard 继续作为智能体与会话控制台
- 不引入本地账号/密码认证
- 管理面板访问控制继续通过网络边界与“管理访问”开关实现

### 4. 每个阶段都应可单独发布

每一阶段都应满足：

- 代码可运行
- smoke 可通过
- README 或 docs 同步更新
- 不依赖“后面阶段完成后才成立”

## 阶段总览

### Phase 0：基线固化

目标：把当前行为和关键假设固定下来，避免后续重构时发生“行为回归但没人发现”。

### Phase 1：统一默认配置来源

目标：消除安装默认值、恢复默认值和运行期默认值的重复定义。

### Phase 2：收敛高频配置写回接口

目标：降低整份配置读改写回带来的覆盖风险。

### Phase 3：拆分前端主控制器

目标：降低 `management.js` 的维护复杂度。

### Phase 4：统一备份与升级边界

目标：让手动备份与升级恢复使用同一份备份规格定义。

### Phase 5：扩展自动测试到关键能力链路

目标：让测试从“服务能起来”升级到“高风险流程可回归”。

### Phase 6：细化接口错误语义与运维文档

目标：降低前端错误处理混乱度，补齐部署与故障文档。

## Phase 0：基线固化

### 目的

当前项目已经可用，重构前必须先固定基线，避免后续改动引入隐式回归。

### 任务

1. 整理并确认以下“当前行为即预期行为”的基线：
   - Management API 默认监听 `0.0.0.0`
   - dashboard 通过 `/dashboard` 代理访问
   - 管理面板不引入本地认证
   - 管理访问通过网络边界和开关控制
   - 插件安装后需要自动修正 `plugins.allow`
   - 技能启用/禁用通过 `openclaw.json.skills.entries` 生效

2. 为现有 smoke 明确覆盖范围并写入文档：
   - 静态资源响应
   - API 基本可访问
   - dashboard fallback 页面可用

3. 为后续重构建立最小回归清单。

### 验收标准

- [README.md](../README.md) 与 [PROJECT_ANALYSIS.md](./PROJECT_ANALYSIS.md) 的运行边界描述一致
- [`test/smoke.sh`](../test/smoke.sh) 的覆盖范围有明确说明
- 团队对“哪些行为不能在重构中被改变”有统一口径

## Phase 1：统一默认配置来源

### 目的

当前默认配置存在多处定义：

- [`cmd/install_callback`](../cmd/install_callback)
- [`app/server/services/config.js`](../app/server/services/config.js)
- 部分前端默认表单值

这些定义长期必然漂移。

### 任务

1. 新建一个统一的默认配置构建模块，例如：
   - `app/server/core/default-config.js`

2. 将以下逻辑统一由该模块生成：
   - gateway 默认配置
   - control UI 默认配置
   - reload 默认配置
   - plugins 默认配置
   - agents defaults 默认配置

补充约束：

- `gateway.bind` 默认值保持 `lan`
- 这里的 `lan` 语义是“监听所有网卡/允许局域网访问”，不是仅本机回环
- 后续 Phase 不应把该默认值收紧成仅本机绑定，除非是明确产品决策变更

3. 安装脚本改为调用统一构建逻辑，而不是手写内嵌 patch 片段。

4. `resetConfig()` 的 fallback 默认配置改为复用同一来源。

5. 对前端“新增模型/渠道”的默认表单值进行一次核对，确保不与后端默认配置发生语义冲突。

### 产出

- 一个统一默认配置生成模块
- 安装与重置逻辑不再各自维护默认值

### 验收标准

- 安装初始化与配置重置得到的关键默认项一致
- 相关默认字段只保留一个后端权威来源
- smoke 通过

### 风险

- 安装脚本是 shell 环境，调用 Node 模块时要注意路径与运行环境一致性

## Phase 2：收敛高频配置写回接口

### 目的

当前大量前端操作采用：

1. `GET /api/config`
2. 本地修改对象
3. `POST /api/config`

这会增加多标签页覆盖风险，也让前端承担过多配置拼装责任。

### 任务

1. 为高频局部操作补充语义化 API：
   - `POST /api/models/primary`
   - `POST /api/channels/upsert`
   - `POST /api/channels/delete`
   - `POST /api/tools/profile`

2. 保留 `POST /api/config` 给：
   - JSON 编辑器
   - 导入配置
   - 高级用户全量编辑

3. 前端高频操作逐步切换到新接口。

4. 在接口层增加更细粒度参数校验，避免前端必须构造整份配置。

### 产出

- 一组局部语义化 API
- 前端高频操作减少整份配置写回依赖

### 验收标准

- 主模型切换不再依赖完整配置 round-trip
- 渠道新增/编辑/删除不再依赖完整配置 round-trip
- 原有配置编辑器仍然可用

### 风险

- 需要谨慎处理新旧接口并存期，避免前后端切换时出现状态不一致

## Phase 3：拆分前端主控制器

### 目的

[`app/ui/assets/management.js`](../app/ui/assets/management.js) 当前仍然承担过多职责，是最明显的维护瓶颈。

### 拆分建议

按功能拆为以下文件：

- `management.dashboard.js`
- `management.models.js`
- `management.channels.js`
- `management.system.js`
- `management.skills.js`

保留以下公共模块：

- `management.state.js`
- `management.editor.js`
- `dom-refs.js`
- `channels.js`

### 任务

1. 先抽离 dashboard 和 system 相关逻辑，因为它们与模型/渠道表单耦合最弱。
2. 再抽离 models 与 channels。
3. 最后保留一个轻量 `management.js` 作为初始化与总线入口。

### 验收标准

- `management.js` 明显瘦身，只保留初始化与公共调度逻辑
- 各模块仅负责一个 tab 或一类能力
- 现有 UI 行为不变
- smoke 通过

### 风险

- 全局函数和 HTML 内联事件较多，拆分时要注意加载顺序与全局暴露方式

## Phase 4：统一备份与升级边界

### 目的

当前手动备份和升级前备份使用相同思路，但边界规格维护在两处：

- shell 升级脚本
- Node 备份服务

这会导致长期漂移。

### 任务

1. 抽象出统一的“备份规格清单”。

候选方案：

- 方案 A：新增一个 JSON 规格文件，shell 和 Node 都读取
- 方案 B：Node 生成规格，shell 通过命令调用读取

2. 统一以下备份项：
   - `.openclaw`
   - `plugins`
   - `extensions`
   - 关键插件 `node_modules`
   - skillhub 相关目录

3. 升级恢复与手动备份都基于同一规格清单执行。

### 验收标准

- 升级前备份项与手动导出备份项保持一致
- 新增备份项时只需要改一个来源

### 风险

- shell 侧读取结构化规格时会比当前脚本复杂一些，需要控制实现复杂度

## Phase 5：扩展自动测试到关键能力链路

### 目的

当前测试偏向存活检查，无法覆盖最有价值的高风险流程。

### 任务

1. 新增配置回归测试：
   - 主模型切换
   - 模型增删改
   - 渠道增删改
   - API key 模式切换的基本行为

2. 新增升级/恢复测试：
   - 准备最小配置目录
   - 执行升级前后脚本
   - 验证恢复结果

3. 新增插件/技能状态测试：
   - 插件状态识别
   - `plugins.allow` 修正
   - 技能启用/禁用写入

4. 保持 smoke 为最小快速检查，不把所有测试都塞进 smoke。

### 验收标准

- 除 smoke 外，至少存在一组“关键能力链路测试”
- 高风险路径的回归成本显著降低

### 风险

- 一部分测试需要 mock 外部依赖或准备本地假数据目录

## Phase 6：细化接口错误语义与运维文档

### 目的

当前很多错误最终都折叠成 `500`，不利于前端稳定处理，也不利于排障。

### 任务

1. 统一接口错误分类：
   - `400`：参数错误 / 校验失败
   - `403`：访问控制拒绝
   - `404`：目标不存在
   - `409`：状态冲突
   - `500`：内部异常

2. 前端 `apiRequest()` 对错误类型做更清晰的处理。

3. 补充部署文档：
   - fnOS 默认中继访问
   - 内网直连访问
   - frp/frps 反向代理访问
   - 管理访问开关的语义

### 验收标准

- 常见用户错误不再统一表现为 `500`
- README 与 docs 中存在明确的部署边界说明

## 推荐实施顺序

按投入产出比，建议顺序如下：

1. Phase 0：基线固化
2. Phase 1：统一默认配置来源
3. Phase 2：收敛高频配置写回接口
4. Phase 3：拆分前端主控制器
5. Phase 4：统一备份与升级边界
6. Phase 5：扩展自动测试
7. Phase 6：细化错误语义与运维文档

## 每阶段执行模板

建议每个阶段按以下模板推进：

1. 明确改动范围
2. 先补或更新测试
3. 再做实现
4. 最后更新 README / docs / changelog

## 近期可直接开工的任务

如果只挑最值得马上做的 3 项，建议是：

1. 统一默认配置生成器
2. 为主模型切换和渠道写入补语义化 API
3. 拆出 `management.system.js` 和 `management.dashboard.js`

## 最终目标

本实施计划的最终目标不是把项目“重写得更漂亮”，而是让 OC-Deploy 继续保持当前产品边界的同时，逐步具备以下能力：

- 默认值一致
- 配置操作更安全
- 前端更易维护
- 备份与升级更可预测
- 高风险流程可回归
- 文档与运行边界一致

做到这些之后，项目就会从“经验驱动的可用工具”进一步演进为“结构稳定的部署平台”。
